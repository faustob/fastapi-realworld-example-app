- qr-otel-version-pin (`pyproject.toml`): opentelemetry-api is pinned at 1.27.0, but this job targets the OTel 1.44 line (default-latest). Different PRs against one repo pinning different OTel lines makes the dependency move for no stated reason.
- qr-metric-naming (`app/core/telemetry.py`): The new instrument name 'flow.entry.count' does not match the platform-prescribed name for flow entries ('flow.entries'), and its '.count' suffix contradicts the semconv 'plain counts are unsuffixed' style used by the other new names (flow.outcomes, flow.validation.outcomes).
- qr-export-pipeline (`app/core/telemetry.py`): The BatchSpanProcessor/PeriodicExportingMetricReader exporters are never flushed or shut down on process exit, and no atexit/shutdown hook or FastAPI shutdown handler is registered for the providers, so buffered spans and metrics can be lost when the process terminates.
- qr-export-pipeline (`app/core/telemetry.py`): The app runs under uvicorn/gunicorn; if deployed with a pre-fork worker model, building BatchSpanProcessor at import time in app/main.py (parent) before fork inherits a background export thread lock and risks a child deadlock, since provider setup runs at module import rather than post-fork.
- qr-preserves-behavior (`app/core/telemetry.py`): os.register_at_fork(after_in_child=_build_and_register_providers) unconditionally rebuilds and re-registers providers in the child of ANY fork. Because create_new_article holds module-level instrument references bound at import (before fork), those proxies rebind fine, but re-registering a brand-new MeterProvider/TracerProvider in every forked child is only correct for pre-fork servers; the module docstring states uvicorn runs single-process, so this hook adds fork-time work with no configured pre-fork model.
