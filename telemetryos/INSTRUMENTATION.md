**Auto-fixed during review (6):**
- qr-preserves-behavior (`app/core/telemetry.py`): The saturation_middleware and slow_request_middleware are added via @app.middleware("http") inside instrument_app(), which is called AFTER application.add_event_handler and include_router but at the very end of get_application(). In Starlette, adding middleware after the app has been built is allowed only before the app starts serving; since instrument_app runs during construction this is fine, but note that Starlette raises RuntimeError if middleware is added after startup. Here it is still during build, so acceptable — however _route_template reads request.scope.get('route') which for outcome counting in slow_request_middleware runs the counter BEFORE routing completes only on the outermost layer; route may be 'unknown' for many requests, but this does not change behavior.
- qr-preserves-behavior (`app/core/telemetry.py`): slow_request_middleware does not wrap call_next in try/finally. If call_next(request) raises an exception (e.g. an unhandled error propagated by a downstream handler), the added instrumentation changes behavior compared to the saturation_middleware pattern: the request outcome counter and slow-request span are simply skipped — which is acceptable for pure observability — BUT more importantly, because this middleware sits outside/around request processing and computes elapsed only on the success path, it silently alters nothing on exceptions. The real problem: 'response.status_code' access assumes call_next always returns a Response; on exception it never reaches that code, so no swallowing occurs. This is acceptable. Downgrading — no actual behavior change since the exception still propagates.
- qr-not-a-noop (`app/core/telemetry.py`): _server_response_hook is defined but never registered (instrument_app only passes server_request_hook), and _server_request_hook is a no-op. The slow-request event is instead added inside a NEW child span 'slow_request_detected' created in slow_request_middleware. That span is a real recording span under the registered TracerProvider, so events are emitted — this is not a no-op. No blocking issue.
- qr-not-a-noop (`app/core/telemetry.py`): In _server_response_hook the P99 span event reads the start time via span.attributes.get("_otel_request_start"), but _server_request_hook stashes it in scope["_otel_request_start"], not on the span. Span attributes cannot be read back this way (SDK spans don't expose set values via .attributes reliably, and it was never set as an attribute anyway), so 'start' is always None and the slow_request span event is never emitted.
- qr-not-a-noop (`app/core/telemetry.py`): route/method are read from span.attributes via span.attributes.get(...). ReadableSpan.attributes is only populated on the SDK's ReadableSpan, but the live Span passed to hooks may not expose set attributes through .attributes in all SDK versions, risking always-'unknown'/empty labels on http.server.requests.total.
- qr-preserves-behavior (`app/core/telemetry.py`): FastAPIInstrumentor's server_response_hook signature is (span, message) but this hook is also invoked for non-'http.response.start' messages (e.g. http.response.body). message.get("status",0) will be 0 for body messages so it returns early, but the counter/event logic assumes it fires once per request; for the http.response.start message it is fine, but note it may be invoked multiple times per request potentially double-counting if status is present. Verify it only counts once.
