- qr-not-a-noop (`app/main.py`): trace.StatusCode.ERROR does not exist. The status code enum is opentelemetry.trace.StatusCode but setting a span status requires a Status object: current_span.set_status(Status(StatusCode.ERROR, ...)). Also `trace.StatusCode` is not exported directly on the `trace` module in the same way as used — StatusCode must be imported from opentelemetry.trace.status (or opentelemetry.trace.StatusCode) and set_status takes a Status. This raises AttributeError/TypeError at runtime, breaking the middleware on every 500 response.
- qr-not-a-noop (`app/telemetry.py`): Same invalid API usage: span.set_status(trace.StatusCode.ERROR, ...). trace.StatusCode is not a valid attribute path and set_status expects a Status object, so record_validation_step raises when a step fails.
- qr-not-a-noop (`app/telemetry.py`): app/telemetry.py creates its own instruments (auth.attempts, flow.outcomes, etc.) at module import time via metrics.get_meter(__name__). If this module is imported before app.main runs its metrics.set_meter_provider(...) bootstrap, get_meter() binds to the default no-op ProxyMeterProvider and these instruments will silently never emit. The comment claims they 'resolve to the same global MeterProvider' but instruments are bound at creation time. Import ordering must guarantee app.main's bootstrap runs first.
- qr-preserves-behavior (`app/main.py`): The active-requests up-down counter is incremented before call_next and decremented after, but if call_next raises an exception the decrement (and duration record) never runs, leaking the active-request count and skewing the gauge. Original behavior (exception propagation) is preserved but the added instrumentation is not exception-safe.

The main.py duplicates with the same instrument names create duplicate-instrument registration on the same meter name/version, which OpenTelemetry treats as identical instruments only if identical; here they are identical so they merge, but the main.py copies are pure dead code. More importantly, this duplication risks divergence and confusion. - ⚠ qr-not-a-noop (`app/telemetry.py`:8): app/telemetry.py calls trace.get_tracer(__name__) at module import time (module-level _tracer). If telemetry.py is imported before app.main runs trace.set_tracer_provider(), the tracer will bind to the default no-op ProxyTracer. OpenTelemetry's proxy tracer does delegate to the real provider once set, so this is generally safe, but only because get_tracer returns a proxy — the lazy pattern used for meters was intentionally not applied to the tracer. This is inconsistent and relies on proxy delegation; acceptable but fragile if import ordering changes. — _For consistency and safety, also lazily resolve the tracer inside _get_instruments() or document reliance on the ProxyTracer delegation._
- ⚠ qr-preserves-behavior (`app/main.py`:118): The @application.middleware("http") metrics middleware is added AFTER FastAPIInstrumentor.instrument_app is not yet called at that point, but note the custom middleware records http.server.request.duration-equivalent metrics while FastAPIInstrumentor also emits its own http.server duration metric. Additionally the custom middleware uses request.url.path as http.route, which yields the raw (unparameterized) path producing high-cardinality metric attributes (e.g. /users/123), risking metric cardinality explosion — a runtime/observability hazard, not a behavior change of the app itself. — _Use the matched route template (request.scope['route'].path or the FastAPI route pattern) instead of request.url.path to avoid unbounded cardinality in http.route._
